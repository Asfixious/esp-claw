## 定位

`cap_im_platform` 是 ESP-Claw 的 IM 平台后端组件。它把飞书、QQ、Telegram、微信以及共享附件处理实现放在同一个 ESP-IDF 组件中，并统一接入 `claw_im_gateway`。

公开发送接口只属于 `cap_im_gateway` Group：

| Capability | 路由字段 | 说明 |
|------------|----------|------|
| `send_message` | `channel + chat_id` | 发送文本 |
| `send_image` | `channel + chat_id` | 发送本地图片 |
| `send_file` | `channel + chat_id` | 发送本地文件 |

平台 Group 只保留连接生命周期和事件源；它们向 Gateway 私下注册发送后端，不再向 Agent 暴露平台前缀工具：

| 平台 Group | channel | 事件源 | 后端发送支持 |
|------------|---------|--------|--------------|
| `cap_im_feishu` | `feishu` | `feishu_gateway` | 文本、图片、文件 |
| `cap_im_qq` | `qq` | `qq_gateway` | 文本、图片、文件 |
| `cap_im_tg` | `telegram` | `tg_gateway` | 文本、图片、文件 |
| `cap_im_wechat` | `wechat` | `wechat_gateway` | 文本、图片 |
| `cap_im_local` | `web` / `local` | `local_gateway` | 文本 |

## 运行模型

每个 IM 后端都遵循同一组职责：

1. **事件源**：从 IM 平台接收消息并交给 `claw_im_gateway` 归一化；应用决定如何进入 Session / Event Router。
2. **私有发送后端**：向 Gateway 注册 channel 与文本/媒体发送回调，不注册平台专属 Capability。
3. **附件处理**：把入站媒体保存到配置的 inbox 根目录，并发布 `attachment_saved` 事件供下游规则处理。

```d2
im_api: "IM 平台 API"
backend: "平台后端\n(飞书 / QQ / Telegram / 微信)"
gateway: "claw_im_gateway"
ingress: "应用入站策略"
router: "claw_event_router"
adapter: "cap_agent\nRPC + event pump"
agent: "claw-agent\nSession"
fatfs: "FATFS inbox"
tools: "统一发送 API\nsend_message / send_image / send_file"

im_api -> backend: "入站消息"
backend -> gateway: "归一化入站"
gateway -> ingress: "统一事件"
ingress -> router: "message / attachment_saved"
backend -> fatfs: "保存附件"
router -> adapter: "call_cap(\"agent\")"
adapter -> agent: "session.input"
agent -> adapter: "Session stream"
adapter -> router: "out_message 事件"
agent -> tools: "LLM 工具调用"
router -> tools: "最终回复"
tools -> gateway: "channel + chat_id"
gateway -> backend: "选择私有后端"
backend -> im_api: "出站文本/媒体"
```

## 启动与可见性

应用启动时会先注册 `cap_im_gateway`，再按启用的平台准备凭证、附件配置和运行时 Group。平台注册时把自己的 channel 与私有发送回调交给 Gateway；Event Router 不维护出站绑定表。

统一 IM Skill 在 `cap_groups` 中只声明 `cap_im_gateway`。激活该 Skill 后，模型获得三个统一工具及 channel 路由说明，不会看到平台专属发送工具。

<Aside type="note">
  `cap_im_platform` 是源码组件，不是公开发送 Group。保留按平台划分的 Group 是为了独立管理各连接的配置、启动与停止状态。
</Aside>

## 平台差异

| 平台 | 入站模型 | 会话目标 | 说明 |
|------|----------|----------|------|
| 飞书 | WebSocket/Event API | 飞书 `chat_id`，或以 `ou_` 开头的用户 `open_id` | 文本优先使用支持 Markdown 的交互卡片，失败后回退纯文本。媒体 caption 会作为后续文本发送。 |
| QQ | QQ Bot WebSocket API | `c2c:<openid>` 或 `group:<group_openid>` | 文件发送依赖 QQ 平台侧支持；图片和通用文件使用不同工具。 |
| Telegram | Bot API 长轮询 | 数字 chat id，例如 `123456789` 或 `-100...` | 长文本会自动分片，文件通过 multipart 流式上传。 |
| 微信 | ClawBot 轮询 API | 明确的群 id 或联系人 id | 支持文本和图片发送，暂不支持通用非图片文件发送。 |
| Web（本地） | HTTP/WebSocket（Web 前端） | `web` channel | 独立组件 `cap_im_local`，用于 Web 配置页内置的 IM 对话界面，支持文本发送。 |

## Telegram 作为代表实现

Telegram 仍是一个适合阅读的代表实现，因为它完整展示了 IM 后端的典型路径：长轮询入站、去重、异步附件下载，以及文本/媒体发送工具。

```d2
tg_api: "Telegram Bot API"
poll_task: "tg_poll_task\n(FreeRTOS)"
router: "claw_event_router"
core: "claw_core\n(Agent)"
attach_queue: "attachment_queue"
attach_task: "tg_attachment_task\n(FreeRTOS)"
fatfs: "FATFS"

tg_api -> poll_task: "getUpdates\n(长轮询, 20 s)"
poll_task -> router: "文本消息\npublish_message()"
router -> core: "Event Router 规则"
poll_task -> attach_queue: "附件（图片/文件）"
attach_queue -> attach_task
attach_task -> tg_api: "getFile -> 下载 URL"
attach_task -> fatfs: "流式写入"
attach_task -> router: "attachment_saved 事件"

llm_call: "统一工具调用\nsend_message\nsend_image / send_file"
gateway: "claw_im_gateway\nchannel=telegram"
llm_call -> gateway
gateway -> tg_api: "sendMessage\nsendPhoto / sendDocument"
```

### 事件源：长轮询机制

Telegram 后端在 `cap_im_tg` Group 的 `start` 钩子中启动两个 FreeRTOS 任务。

`tg_poll_task` 持续调用 `getUpdates`（带 20 秒 long-poll 超时），将收到的每条消息解析后发布到 Gateway：

```c
claw_im_gateway_publish_inbound(&(claw_im_gateway_inbound_event_t){
    .source_cap = "tg_gateway",
    .channel = "telegram",
    .chat_id = chat_id,
    .sender_id = sender_id,
    .message_id = message_id,
    .event_type = "message",
    .content_type = "text",
    .text = text,
});
```

`claw_event_router` 收到此事件后，根据规则决定是交给 `claw_core` 运行 Agent，还是触发自动化动作。

### 去重缓存

由于网络抖动可能导致同一更新被重复下发，`cap_im_tg` 维护了一个循环 FNV-1a 哈希缓存，避免同一消息被处理两次：

```c
#define CAP_IM_TG_DEDUP_CACHE_SIZE 64

static bool cap_im_tg_dedup_check_and_record(const char *update_key)
{
    uint64_t key = cap_im_tg_fnv1a64(update_key);
    for (size_t i = 0; i < CAP_IM_TG_DEDUP_CACHE_SIZE; i++) {
        if (s_tg.seen_update_keys[i] == key) return true; // 已见过
    }
    s_tg.seen_update_keys[s_tg.seen_update_idx] = key;
    s_tg.seen_update_idx = (s_tg.seen_update_idx + 1) % CAP_IM_TG_DEDUP_CACHE_SIZE;
    return false;
}
```

### 附件处理

附件（图片/文档）的下载是耗时操作，Telegram 后端会异步处理：

1. `tg_poll_task` 将 `cap_im_tg_attachment_job_t` 放入队列。
2. `tg_attachment_task` 消费队列，调用 `getFile` 获取下载 URL，流式写入 FATFS。
3. 下载完成后发布 `attachment_saved` 事件，携带本地路径、MIME、尺寸与平台元数据。

```c
// attachment_saved 事件的 payload_json 示例
{
  "platform": "telegram",
  "attachment_kind": "photo",
  "saved_path": "/fatfs/inbox/telegram/-123456/789/photo.jpg",
  "saved_dir": "/fatfs/inbox/telegram/-123456/789",
  "saved_name": "photo.jpg",
  "mime": "image/jpeg",
  "caption": "看看这个",
  "platform_file_id": "AgACAgIAAxkBAAI...",
  "size_bytes": 45231,
  "saved_at_ms": 1714000000000
}
```

下游规则可以监听 `attachment_saved` 事件，触发 `cap_llm_inspect`、文件操作或自定义自动化动作。

### 可调用工具

`cap_im_gateway` 注册三个公开 Capability；`cap_im_tg` 只保留 `tg_gateway` 事件源和私有发送实现：

| 工具 ID | 描述 | kind |
|---------|------|------|
| `send_message` | 按 channel 与 chat_id 发送文本 | `CALLABLE` |
| `send_image` | 按 channel 与 chat_id 发送本地图片 | `CALLABLE` |
| `send_file` | 按 channel 与 chat_id 发送本地文件 | `CALLABLE` |

主动发送时可显式提供路由；回复当前会话时也可由调用上下文继承：

```lua
capability.call("send_message", {
  message = "hello"
}, {
  channel = "telegram",
  chat_id = "123456789"
})
```

路由优先使用调用上下文中的显式 target，其次使用输入 JSON，最后继承当前来源上下文。Telegram 私有后端仍会自动分片超长文本；图片和文件仍通过 multipart/form-data 流式上传。

### 配置 API

应用层通过 `cap_im_platform` 导出的 `cap_im_tg_*` API 配置 Telegram 后端：

```c
// 设置 Bot Token（必须在 start 前调用）
cap_im_tg_set_token("YOUR_BOT_TOKEN");

// 配置附件接收（可选）
cap_im_tg_set_attachment_config(&(cap_im_tg_attachment_config_t){
    .storage_root_dir         = "/fatfs/inbox",
    .max_inbound_file_bytes   = 2 * 1024 * 1024,  // 最大 2 MB
    .enable_inbound_attachments = true,
});

// 手动启动（通常由 claw_cap_start_group 调用）
cap_im_tg_start();
```

其他后端使用相同的架构角色，只是在认证方式、消息格式和媒体 API 上存在平台差异。
