## Role

`cap_im_platform` is the IM platform backend component for ESP-Claw. It bundles the Feishu, QQ, Telegram, WeChat, and shared attachment implementations into one ESP-IDF component and connects all of them to `claw_im_gateway`.

Only the `cap_im_gateway` group exposes public send APIs:

| Capability | Route fields | Description |
|------------|--------------|-------------|
| `send_message` | `channel + chat_id` | Send text |
| `send_image` | `channel + chat_id` | Send a local image |
| `send_file` | `channel + chat_id` | Send a local file |

Platform groups retain connection lifecycle and event sources. They privately register send backends with the Gateway instead of exposing platform-prefixed tools to the Agent:

| Platform group | channel | Event source | Backend send support |
|----------------|---------|--------------|----------------------|
| `cap_im_feishu` | `feishu` | `feishu_gateway` | Text, image, file |
| `cap_im_qq` | `qq` | `qq_gateway` | Text, image, file |
| `cap_im_tg` | `telegram` | `tg_gateway` | Text, image, file |
| `cap_im_wechat` | `wechat` | `wechat_gateway` | Text, image |
| `cap_im_local` | `web` / `local` | `local_gateway` | Text |

## Runtime model

Each backend follows the same split:

1. **Event source**: receive messages from the IM platform and hand them to `claw_im_gateway` for normalization; the application decides how they enter Session / Event Router.
2. **Private send backend**: register channel-specific text/media callbacks with the Gateway, without registering platform-specific capabilities.
3. **Attachment handling**: save inbound media under the configured inbox root and publish `attachment_saved` events for downstream rules.

```d2
im_api: "IM platform API"
backend: "platform backend\n(Feishu / QQ / Telegram / WeChat)"
gateway: "claw_im_gateway"
ingress: "application ingress policy"
router: "claw_event_router"
adapter: "cap_agent\nRPC + event pump"
agent: "claw-agent\nSession"
fatfs: "FATFS inbox"
tools: "unified send API\nsend_message / send_image / send_file"

im_api -> backend: "inbound messages"
backend -> gateway: "normalized ingress"
gateway -> ingress: "unified event"
ingress -> router: "message / attachment_saved"
backend -> fatfs: "save attachments"
router -> adapter: "call_cap(\"agent\")"
adapter -> agent: "session.input"
agent -> adapter: "Session stream"
adapter -> router: "out_message event"
agent -> tools: "LLM tool call"
router -> tools: "final reply"
tools -> gateway: "channel + chat_id"
gateway -> backend: "select private backend"
backend -> im_api: "outbound text/media"
```

## Startup and visibility

Application startup registers `cap_im_gateway`, then prepares credentials, attachment settings, and runtime groups for enabled platforms. Each platform registers its channel and private send callbacks with the Gateway; Event Router has no outbound binding table.

The unified IM Skill declares only `cap_im_gateway` in `cap_groups`. Activating it gives the model the three unified tools and channel routing guidance, without exposing platform-specific send tools.

<Aside type="note">
  `cap_im_platform` is a source component, not a public send group. Per-platform groups remain so each connection can manage its configuration, start, and stop state independently.
</Aside>

## Platform differences

| Platform | Inbound model | Chat target | Notes |
|----------|---------------|-------------|-------|
| Feishu | WebSocket/Event API | Feishu `chat_id`, or user `open_id` beginning with `ou_` | Text sends prefer Markdown-capable interactive cards with plain-text fallback. Media captions are sent as follow-up text. |
| QQ | QQ Bot WebSocket API | `c2c:<openid>` or `group:<group_openid>` | File delivery depends on QQ platform support; image and generic file paths are separate tool calls. |
| Telegram | Bot API long polling | Numeric chat id such as `123456789` or `-100...` | Long text is chunked and files are uploaded with multipart streaming. |
| WeChat | ClawBot polling API | Concrete room id or contact id | Text and image sends are supported; generic non-image file send is not available. |
| Web (local) | HTTP/WebSocket (Web frontend) | `web` channel | Separate `cap_im_local` component for the built-in IM chat UI on the Web config page; supports text sending. |

## Telegram as a reference backend

Telegram remains a useful representative implementation because it shows the full pattern in a compact backend: long-poll ingress, deduplication, async attachment downloads, and callable text/media sends.

```d2
tg_api: "Telegram Bot API"
poll_task: "tg_poll_task\n(FreeRTOS)"
router: "claw_event_router"
core: "claw_core\n(Agent)"
attach_queue: "attachment_queue"
attach_task: "tg_attachment_task\n(FreeRTOS)"
fatfs: "FATFS"

tg_api -> poll_task: "getUpdates\n(long poll, 20 s)"
poll_task -> router: "text\npublish_message()"
router -> core: "Event Router rules"
poll_task -> attach_queue: "attachments (image/file)"
attach_queue -> attach_task
attach_task -> tg_api: "getFile -> download URL"
attach_task -> fatfs: "stream write"
attach_task -> router: "attachment_saved event"

llm_call: "unified tool calls\nsend_message\nsend_image / send_file"
gateway: "claw_im_gateway\nchannel=telegram"
llm_call -> gateway
gateway -> tg_api: "sendMessage\nsendPhoto / sendDocument"
```

### Event source: long polling

The Telegram backend starts two FreeRTOS tasks from the `cap_im_tg` group `start` hook.

`tg_poll_task` calls `getUpdates` with a 20 s long-poll timeout, parses each update, and publishes it to the Gateway:

```c
claw_im_gateway_publish_inbound(&(claw_im_gateway_inbound_event_t){
    .source_cap = "tg_gateway",
    .channel = "telegram",
    .chat_id = chat_id,
    .sender_id = sender_id,
    .message_id = message_id,
    .event_type = "message",
    .content_type = "text",
    .text = text,
});
```

`claw_event_router` then routes the event to `claw_core` for the Agent or to automation actions.

### Dedup cache

Network jitter can replay updates; `cap_im_tg` keeps a ring of FNV-1a 64-bit hashes so the same message is not handled twice:

```c
#define CAP_IM_TG_DEDUP_CACHE_SIZE 64

static bool cap_im_tg_dedup_check_and_record(const char *update_key)
{
    uint64_t key = cap_im_tg_fnv1a64(update_key);
    for (size_t i = 0; i < CAP_IM_TG_DEDUP_CACHE_SIZE; i++) {
        if (s_tg.seen_update_keys[i] == key) return true; // seen
    }
    s_tg.seen_update_keys[s_tg.seen_update_idx] = key;
    s_tg.seen_update_idx = (s_tg.seen_update_idx + 1) % CAP_IM_TG_DEDUP_CACHE_SIZE;
    return false;
}
```

### Attachments

Media download is slow, so Telegram handles it asynchronously:

1. `tg_poll_task` enqueues `cap_im_tg_attachment_job_t` items into a queue.
2. `tg_attachment_task` consumes jobs, calls `getFile`, and streams the payload into FATFS.
3. On completion it publishes `attachment_saved` with local path, MIME, size, and platform metadata.

```c
// Example attachment_saved payload_json
{
  "platform": "telegram",
  "attachment_kind": "photo",
  "saved_path": "/fatfs/inbox/telegram/-123456/789/photo.jpg",
  "saved_dir": "/fatfs/inbox/telegram/-123456/789",
  "saved_name": "photo.jpg",
  "mime": "image/jpeg",
  "caption": "Look at this",
  "platform_file_id": "AgACAgIAAxkBAAI...",
  "size_bytes": 45231,
  "saved_at_ms": 1714000000000
}
```

Downstream rules can listen for `attachment_saved` and chain `cap_llm_inspect`, file operations, or custom automation.

### Callable tools

`cap_im_gateway` registers three public capabilities; `cap_im_tg` retains only the `tg_gateway` event source and private send implementation:

| Tool ID | Description | kind |
|---------|-------------|------|
| `send_message` | Send text by channel and chat_id | `CALLABLE` |
| `send_image` | Send a local image by channel and chat_id | `CALLABLE` |
| `send_file` | Send a local file by channel and chat_id | `CALLABLE` |

Proactive sends may provide an explicit route; replies can inherit the current call context:

```lua
capability.call("send_message", {
  message = "hello"
}, {
  channel = "telegram",
  chat_id = "123456789"
})
```

Routing prefers an explicit target in the call context, then input JSON, then the current source context. The private Telegram backend still chunks long text and streams image/file multipart uploads.

### Configuration API

Application code configures the Telegram backend through the `cap_im_tg_*` API exported by `cap_im_platform`:

```c
// Bot token (must be set before start)
cap_im_tg_set_token("YOUR_BOT_TOKEN");

// Optional inbound attachment policy
cap_im_tg_set_attachment_config(&(cap_im_tg_attachment_config_t){
    .storage_root_dir         = "/fatfs/inbox",
    .max_inbound_file_bytes   = 2 * 1024 * 1024,  // max 2 MB
    .enable_inbound_attachments = true,
});

// Manual start (normally via claw_cap_start_group)
cap_im_tg_start();
```

The same architectural roles are used by the other backends, with platform-specific authentication, message formats, and media APIs.
