# ADR-0005: Owner 定义的类型化持久化

- Status: Accepted
- Date: 2026-08-07

## Context

会话、记忆、技能索引和配置需要跨重启保留。设备可能在写入期间掉电，schema 会随版本变化，底层存储也可能返回不存在、损坏、容量不足或 I/O 失败。

如果持久化层持有一个无类型 key-value 字典，字段含义和默认值会散落到调用点；如果读取失败一律回退默认值，数据损坏会被误判为首次启动并造成静默丢失。

## Decision

每种持久状态由定义其领域模型的 owner crate 管理。Owner 定义：

- 类型化 schema 与版本；
- 校验和旧版本迁移；
- dirty generation 与快照时机；
- 不存在、损坏、版本不支持和 I/O 失败的语义。

`claw-persistence` 提供统一的存取协议、编码边界和可靠提交能力；平台 adapter 负责文件、NVS 或分区的实际 I/O。持久化读取失败必须作为类型化错误返回，除非有明确且可观测的恢复策略，否则不静默创建空状态。

## Alternatives

### 全局无类型 key-value 存储

接入快速，但 schema、默认值和迁移逻辑分散，难以审计。

### 所有状态放入一个大型快照

一致性边界直观，但任一模块变化都会耦合整体 schema，写放大和恢复成本高。

### 只保存 JSON/字节，不维护版本

初期简单，但升级后无法可靠区分格式，也难以提供可行动的错误。

### 读取失败自动恢复为空

可提高表面启动成功率，但会掩盖损坏并可能覆盖可恢复数据。

## Consequences

### Positive

- schema 责任与领域模型保持一致；
- 错误分类清晰，损坏不会静默丢失；
- 模块可以独立演进和迁移；
- 测试可以覆盖编码、恢复、迁移和掉电边界；
- dirty generation 可减少不必要的 Flash 写入。

### Negative

- 每个 owner 都要维护版本和迁移测试；
- 跨多个 owner 的原子事务需要额外协调；
- 类型化错误和恢复策略增加 API 设计成本；
- 旧 schema 的长期兼容需要明确淘汰政策。

### Follow-up constraints

- 每次 schema 变化必须更新版本并增加迁移测试；
- 快照提交应使用临时记录、双槽或平台等价机制避免半写；
- 默认值只用于“确实不存在”或明确的新字段；
- 日志应记录恢复来源与错误类别，但不得泄漏敏感内容；
- Flash 写入频率、峰值内存和最大记录大小必须有预算。
