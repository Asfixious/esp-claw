# ADR-0003: 跨多个 Turn 的会话事件流

- Status: Accepted
- Date: 2026-08-07

## Context

Agent 会话不是普通的一问一答。一次输入可能产生流式文本、多个工具调用、权限询问、中断和后续输入；一个会话还要连续承载多个 Turn。

如果每个 Turn 都重新建立回调或连接，上层必须重复绑定状态，工具和审批的异步结果也很难与原会话关联。如果把“当前 Turn 完成”当成“会话关闭”，多轮交互会产生竞态和资源抖动。

## Decision

每个打开的 Session 暴露一个长生命周期、顺序化的事件流。该事件流可跨越多个 Turn，并使用明确的边界事件：

- `TurnEnded`：当前 Turn 已结束，会话仍可继续；
- `Closed`：会话事件流终止，不再接受新输入。

输入、追加、交互回应、中断、取消和关闭通过 `SessionControl` 发送。上层在会话存续期间持续运行事件泵，并负责对 C ABI 事件恰好释放一次。

## Alternatives

### 每个输入返回一个独立 future

对简单请求自然，但不易表达权限询问、工具回调和跨 Turn 状态，也会把事件关联责任推给调用方。

### 每个 Turn 创建和销毁会话

生命周期简单，但无法自然保留会话状态，持久会话恢复和 IM 映射成本更高。

### 仅使用全局事件总线

与设备系统集成方便，但事件归属、顺序和关闭语义需要调用方自行拼装。

## Consequences

### Positive

- 流式文本、工具事件和控制事件共享同一顺序；
- 多轮会话不需要重复初始化；
- 中断、取消和权限回应可以定位到明确 Session；
- C 和 Rust 调用方获得一致的生命周期模型。

### Negative

- 调用方必须持续消费事件并处理背压；
- `TurnEnded` 与 `Closed` 的区别需要文档和测试保护；
- 慢消费者可能阻塞会话，需要有界队列和超时策略；
- 关闭、断连和取消之间的状态组合更复杂。

### Follow-up constraints

- 每个公开示例都应展示正确的终止条件；
- 事件必须能关联 Session、Turn 和 tool call；
- 关闭后发送操作要返回明确错误；
- 测试覆盖连续多个 Turn、消费者提前退出、取消与关闭竞态。
