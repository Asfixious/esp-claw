At minimum, include `claw_event_publisher.h` if you only need to publish events (it automatically includes `claw_event.h`).

## Responsibilities

`claw_event_router` ingests structured `claw_event_t` events, matches them against `router_rules.json` (or rules added/removed at runtime), and runs a chain of actions (for example call a capability, run Lua, send a message, or emit another event).

For the end-to-end flow and full `router_rules.json` syntax, see [Dataflow and automation](@lang/reference-project/dataflow-and-automation).

## Event Sources

Capabilities (especially IM gateways, MCP, etc.) call `claw_event_router_publish_message` or `claw_event_router_publish_trigger` at appropriate times. `cap_agent` exclusively consumes each opened `claw_agent.h` Session stream and publishes completed Agent responses as `out_message` events;
tool calls are translated to `agent_stage` events (see [Dataflow and automation](@lang/reference-project/dataflow-and-automation#agent_stage-event-and-execution-progress-notifications)).

The router processes the queue asynchronously so heavy work does not run on CPU-heavy callback stacks.

## Interaction with cap_agent

Agent input uses the ordinary `call_cap` action with `cap: "agent"` and the RPC envelope `{"method":"session.input","args":{"text":"..."}}`. Event Router forwards the event's Session, request, route, and correlation fields through `claw_cap_call_context_t`. `cap_agent` accepts the input immediately, then publishes complete output back as `source_cap=agent,event_type=out_message`.

Common fields in `claw_event_router_config_t`:

- `default_route_messages_to_agent`: whether certain messages are routed to the Agent when no rule matches.
- `default_route_agent_output_to_channel`: whether unmatched Agent `out_message` events call the unified IM Gateway with their event route.

In `edge_agent`, both default routes are enabled. Explicit matching rules still take priority over either fallback.

<Aside type="caution" title="Agent input still requires a linked LLM API">
  `edge_agent` initializes and starts AgentSystem even when its initial API fields are empty.
  Session input remains unavailable until a valid API binding is linked. Event Router, automation rules, local capabilities, and the Console REPL remain available.
</Aside>

## Queue cancellation and purge

`claw_event_router` provides two pending-event queue management APIs:

- `claw_event_router_cancel_event(event_id)`: cancel (skip) one pending event by `event_id`.
- `claw_event_router_purge_queue(event_type_filter, source_cap_filter, &out_cancelled)`: batch-cancel pending events with optional filtering by `event_type` and `source_cap`, and returns how many were marked.

<Aside type="note">

  - These APIs only affect events that are still pending in the queue, and do not interrupt actions already executing.
  - If the target `event_id` is not found in pending queue items, `claw_event_router_cancel_event` returns `ESP_ERR_NOT_FOUND`.
  - This is useful for fast mitigation, such as clearing an event flood or retracting queued automation events before execution.

</Aside>

## IM Gateway outbound routing

User-facing platform backends hand incoming messages to the IM Gateway for normalization. The Event `channel` identifies the source and becomes the default target channel for follow-on Events.
When the Event Router handles a final send-message Event, it always invokes the `send_message` capability and places the target `channel` and `chat_id` in the call context. The IM Gateway then selects the QQ, Feishu, Telegram, WeChat, or Web backend using `channel + chat_id`.

The Event Router no longer maintains a channel-to-capability binding table, and platforms no longer expose dedicated tools such as `qq_send_message` or `feishu_send_message`.

## Session policy

`claw_event_session_policy_t` affects how `claw_event_build_session_id` derives session ids, and thus how events align with `claw_memory` / `claw_skill` session state.

| Policy | Description |
|------|------|
| `CHAT` | Derived from `source_channel:chat_id`. All messages in the same chat window share a session. |
| `TRIGGER` | Derived from `trigger:source_cap:event_key`. Each trigger source has an independent session. |
| `GLOBAL` | Derived from `global:source_cap`. All events from the same source capability share a global session. |
| `EPHEMERAL` | Derived from `ephemeral:event_id`. Each event gets a unique, one-time session. |
| `NOSAVE` | Generates an empty session id (length 0). Turns are not saved to session history. |

<Aside type="tip">

  If automation or IM shows “mixed memory” or odd Skill activation, check that rule `session_policy` matches the event fields.

</Aside>
